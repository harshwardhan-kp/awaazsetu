# M2 extraction, scoring and duplicate text comparison

`backend.app.m2.triage` exports the three functions in BUILD_CONTRACT.md. Extracted reports are validated with Pydantic v2. With no credentials or `use_ai=False`, deterministic English/Hindi/Marathi rules work offline. Missing fields remain null or unknown; an unrecognized request remains `other`. A local negation window suppresses negated phrases, including nobody/no one/none as well as Hindi/Marathi negatives. English water-entry expressions require a home/house context; generic water entering a road does not count as home flooding. Tense and plural variants such as water is entering homes, water has entered the house, and homes flooded are supported. Water levels require water/flood context in the same sentence: being on a roof alone does not prove roof-level flooding. Counts support Arabic/Devanagari digits and a small written-number vocabulary. Location phrases are preserved for M3, never geocoded by M2.

With `OPENAI_API_KEY` in the process environment, extraction uses OpenAI strict JSON-schema structured output and validates its result against the report schema. `OPENAI_TRIAGE_MODEL` overrides `OPENAI_MODEL`, which defaults to `gpt-4o-mini`; `OPENAI_EMBEDDING_MODEL` defaults to `text-embedding-3-small`. Calls have a 20-second network timeout. Invalid/low-confidence responses and provider errors fall back to rules. No provider error bodies, secrets or resident texts are logged. Resident text is marked as untrusted data in the system prompt. Trapped/medical/home flags determine canonical incident type in that priority order; explicitly positive emergency phrases found by the local rules are retained even if AI misses them. Simple English field-assignment commands are excluded from rule evidence. This is a narrow safeguard, not a proof against prompt injection or malicious reports. AI remains probabilistic and coordinator verification is required. Field-confidence values are heuristic/model estimates, not calibrated probabilities.

The drill score follows the proposal points: rescue 40, medical 30, water entering home 20; exactly one water level (roof/chest 25, waist 15, knee 8); vulnerable residents 15 once; road waterlogging 10 only for road incident type; five or more people 10; night 5; three or more distinct reporters 10. The caller supplies verified unique reporter count and night flag. Total caps at 100. Critical is 70+, high 45+, medium 25+, low below 25. Reasons retain raw points, which can total more than the capped score. Version `drill_policy_v1` makes this explicit. The proposal's example score of 70 for trapped + waist + elderly omits an additional home criterion; implementation counts home only when separately reported, for 90 if all four apply. These thresholds are policy assumptions without field validation.

AI extraction requests a concise English factual summary for every source language in the same extraction call, preserving negation and original place names. The original resident text remains stored separately as report.text. The service may compare these English summaries when both reports were extracted by AI; rule summaries retain original resident text. Similarity returns a value and method. Embeddings can represent multilingual text, but a live English/Marathi equivalent pair scored only approximately 0.285, below the current threshold, so raw multilingual cosine similarity is not a validated duplicate detector. English summary comparison is a mitigation that still requires measured evaluation. Offline lexical similarity blends token Jaccard and character sequence similarity and does **not** establish cross-language duplicates. No duplicate threshold is validated. The parent pipeline must require matching incident type, <=500m and <=3h before automatic merging, with higher thresholds or human review for lexical comparisons. Similar text alone never proves identical residents/events.

Run from the repository root:

```sh
.venv/bin/python -m pytest tests/test_triage.py -q
.venv/bin/python scripts/evaluate.py
```

The dataset contains 150 clearly synthetic cases (50 per language), generated from only five templates per language with count/location variation. This verifies a narrow baseline; 150 successes do not demonstrate real-world extraction accuracy or duplicate F1. It covers rescue, medical, home flooding, road flooding and negated non-incidents. Separate tests cover negation, policy thresholds, score caps, provider failure/schema errors, unknown fields and empty text. Future validation requires independently labelled real/realistic paraphrases, transliteration, code-switching, spelling noise, location ambiguity, and paired duplicate/nonduplicate cases. Avoid reporting this synthetic match rate as a deployed accuracy claim.

`python scripts/evaluate.py --ai` explicitly opts in to external requests and charges; offline is the default. No live provider requests are performed by unit tests. Do not store API keys in code, evaluation output or version control.
